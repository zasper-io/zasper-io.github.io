It speaks Jupyter's wire protocol, so it runs the notebooks you already have.

The gap widens as the load does

Both servers were run against the same workload, 10 requests per second per kernel on an Apple M4, from 2 concurrent kernels up to 100. Zasper uses less of both at every load, and the RAM gap grows with concurrency, from about 4× at 2 kernels to 38× at 100. At 64 kernels Jupyter Server begins losing kernel connections, and by 100 it has lost all of them, while Zasper answers every request at both loads.

CPU is averaged across each run; RAM is the highest figure observed. The figures above round the widest gaps: 4.5× less CPU at 4 kernels and 38× less RAM at 100. At 2 kernels the difference is about 3× for CPU and 4× for RAM. The CPU gap does not grow with load, while the RAM gap does. The crosses are measured the same way as the lines, as replies received against requests sent, which is flat at five replies per request until a server stops answering. Jupyter's 14% CPU at 100 kernels is 14% while returning nothing. Every point is recomputed from the raw runs in zasper-benchmark, where the harness and the methodology are public.

Your notebooks, unchanged

Zasper reads and writes .ipynb directly, so a notebook moves between Zasper and JupyterLab without being converted. Your files stay where they are — no import step, no workspace to create — and the same kernels run them, registered once.

  • Saved as Jupyter would save it, byte for byte, so opening a file here does not turn into a diff or a merge conflict.
  • A notebook keeps its own nbformat version. A 4.2 notebook is saved as 4.2 rather than silently upgraded.
  • The outputs you use render: HTML, PNG, JPEG, SVG, LaTeX through KaTeX, Plotly figures, ipywidgets and JSON.
  • Saves are atomic. Zasper writes beside the file and renames over it, so a crash cannot leave half a notebook.
  • JupyterLab extensions do not carry over. Zasper has its own extension model; a lab extension will not load.
  • Widget state is not written into the file yet. It lives in the kernel, so a widget redraws while the kernel is up and shows a placeholder once it is gone.
  • Notebooks are not signed, as Jupyter signs them. Trust is given per folder instead, and nothing a folder controls runs until you trust it. HTML saved in a notebook's outputs is sanitised when the notebook opens, so its scripts do not run until you run the cell again.

The whole of it, including what each output type needs, is on Notebook Support.

Every kernel you already run

Zasper launches kernels through Jupyter's own kernelspec mechanism, so a kernel that runs under Jupyter runs here — without being registered again.

{% include kernel-row.html %}

Python covers two implementations, ipykernel and Xeus (xeus-python). Every registered kernel is listed, and so is any Python environment Zasper finds with ipykernel in it. The launcher above shows nine, two of them Xeus kernels. Installing kernels walks through adding your own.

Your laptop, or your server

The same binary either way. Run it on the machine in front of you, or put it on a box and open it from anywhere — a footprint this small is what makes a shared server cheap.

Signed in from the first run

Every server starts with an access token. Sign in with the link it prints, or paste the token; set it yourself to keep it across restarts.

Behind your own HTTPS

A reverse proxy in front, WebSockets passed through, and the certificate you already have.

Docker, or a service

A Dockerfile and a Compose file to build and run it in a container, and a systemd unit for when it should come back up with the machine.

Deploying on Cloud walks through all three, and both ways to sign in.

Questions people actually ask

Is Zasper a drop-in replacement for JupyterLab?

For your notebooks and your kernels, yes: the same files, the same kernelspecs, the same wire protocol. For JupyterLab itself, no — this is a separate implementation with its own interface, not a re-creation of Lab's UI or its extension API.

Do my JupyterLab extensions work?

No. Zasper has its own extension model rather than Lab's, so a lab extension will not load. If an extension is the reason you are staying, that is a fair reason to stay.

Does it work on Windows?

Yes, and there is a Windows build. The one part that needs WSL is the built-in terminal, which is built on a Unix pseudo-terminal; running the server under WSL gives you that too and is the setup we recommend.

Is it really free?

Yes, under the AGPL-3.0 — install it, run it, put it on your own server, change it. The commercial license is for building Zasper into a proprietary product, which the AGPL does not allow.

What happens to my conda and uv environments?

One registered as a Jupyter kernel appears in the launcher as it does in Jupyter, without being registered again. Without a kernelspec, Zasper still lists one with ipykernel in it if it is active when Zasper starts, is your base conda install, or is the project's .venv in a trusted folder.

Does my code leave my machine?

No. Zasper runs a server on your own machine and your files stay on it. It sends anonymous usage data, with no file names, paths, contents or IP address, and ZASPER_TELEMETRY=0 switches it off; PRIVACY.md is the complete list. It also asks zasper.io once a day whether there is a newer version, and loads widget libraries it does not bundle from jsDelivr unless Load widget libraries from the internet is off in Settings.
